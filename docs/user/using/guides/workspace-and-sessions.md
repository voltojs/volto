# Workspaces and sessions

> After reading: know what a workspace is, where sessions are stored, and how to find them again and clean them up.

## Workspace

The workspace is the directory where the agent does its work. Once selected, file reads and writes, command execution and git operations all use it as the working directory.

- The workspace list is stored in the `projects` section of `~/.volto/config.json` (`id` / `name` / `path` / `createdAt`).
- The same workspace can host many sessions; they share the filesystem, but their conversation contexts are independent of each other.
- **The workspace is not a security boundary.** It decides "where work happens by default", not "what can be touched" — that is decided by the permission mode and the sandbox. See [Permissions and approvals](./permissions-and-approvals.md).

## Sessions

Each conversation is a persisted record, kept in the session store under `~/.volto/` (JSONL, events appended one by one).

| Capability | How |
| --- | --- |
| Find again | The left-hand list is grouped by workspace; closing the browser or restarting the frontend loses nothing |
| Rename | Session menu → Rename; the title can also be generated by the model (a dedicated model can be designated in settings) |
| Pin | Session menu → Pin. The pinned state is stored gateway-side, so it is the same in another browser |
| Delete | Session menu → Delete session. A session that is currently generating cannot be deleted |
| Export | Session menu → Export session (Markdown); the API also supports JSONL |
| Roll back to a turn | Start a new session from the conversation point before that turn; the original session is kept |
| Compact | `/compact` triggers one context compaction manually |
| Restore after refresh | The browser remembers the currently active session locally; after a refresh it returns to it automatically, and falls back to the welcome screen when the session no longer exists |

A generating session shows a spinner to the left of its title; even if you switch to another session, the icon stays until that turn ends.

The sidebar layout (pins, workspace order, sort order, collapsed state) lives separately in the `sidebar` section of `config.json`. It is **view state** and is not written into the conversation record — otherwise exporting a conversation would carry the "pin" along with it.

## Attachments and file references

- **Images**: paste or drag them straight into the input box. Whether the model can see them depends on whether that model declares image input support.
- **Non-image attachments**: PDFs, text and the like are converted into text blocks and merged into the message (a PDF is parsed up to 50 pages and about 200k characters by default; anything beyond that is stated as truncated).
- **`@` references**: type `@` to pick a file from the workspace and insert a file reference; the reference is resolved into a path or content at send time, which is more reliable than typing the path by hand.

Attachments are stored per session. A background cleanup reclaims the attachment directory of a deleted session after a 24-hour grace period; attachments of sessions that still exist are never reclaimed.

## Audit trail

Besides the conversation itself, every session has an **audit trail**: the input, tool calls, approval decisions and context reminders of every step are recorded in time order. The trajectory view in the UI is a projection of it, there to answer "why did it do that at the time".

The "Request" tab of each model call lists the structure of that request: model, header hash, tool names, message id/role, content block types, tool call/result ids and image attachment refs. It does not store full text or image bytes, so you can see what the request was composed of without large prompts or screenshots being stuffed into the trail. Older sessions written before the upgrade have no such manifest, and their Request tab shows empty.

The raw events can also be fetched directly (`GET /sessions/:id/events`); an exported JSONL comes from the same source.

## Where session snapshots live (sqlite and fallback)

Session snapshots are written to `~/.volto/db/sessions.db` (SQLite) by default. It depends on the native module `better-sqlite3`, which may fail to load on a machine with a different Node version or without the prebuilt binary. In that case Volto does **not** wipe or migrate this database; instead it:

1. prints a warning at startup, stating which directory new sessions are stored in now and which database file is no longer read;
2. switches to file storage under `~/.volto/sessions-store/`, and sessions work as usual;
3. shows `warn (file (fallback: module missing))` on the `sqlite` line of `volto doctor`.

If the driver is installed but the database file itself cannot be opened (permissions, in use, corrupt file), it likewise switches to file storage, but `doctor` shows
`warn (file (fallback: db unusable))`, and the warning states that **this database does exist and is simply not being read**, together with the underlying error code.
Neither case deletes or rewrites `sessions.db`.

The original `sessions.db` sits on disk untouched, and is read again on the next start once the problem is fixed. When `doctor` is healthy this line is `sqlite: ok (sqlite (primary))`. If you know sqlite cannot be used in the current environment, you can set `VOLTO_SESSION_STORE=file` to use file storage explicitly, and `doctor` shows `file (forced)`.

## When something goes wrong

- **A session is missing from the list** → check whether you switched workspace directories (the list is grouped by workspace); or whether the `sqlite` line of `volto doctor` says `file (fallback: …)` — that means old sessions are still in `sessions.db` and the current process simply is not reading it.
- **Opening a session reports it cannot be read** (the API returns 410, saying the session was written by an earlier version) → the current build cannot read it; export it with a version that can, then reopen it.
- **Attachments are gone** → the session was deleted and the attachments were cleaned up with it. Attachments are not reused across sessions.
