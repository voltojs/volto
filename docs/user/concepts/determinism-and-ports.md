# 为什么一切经端口注入

> 读完你会：理解这个项目为什么宁可多写一层接口，也不直接调 `Date.now()`。

## 一条规则

核心不碰 I/O。时间、随机、ID、文件、命令、网络、存储、模型——全部是注入进来的对象。核心只做决策，把「要去做什么」作为效果返回，由外面的执行者去做。

## 换来什么

**1. 可重放。** 同一串输入跑两次，得到逐字节相同的状态与效果序列。这不是理论收益：仓库里的评测就是录下真实轨迹，再离线放一遍，断言完全一致。

**2. 可测试。** 测试里不需要真文件、真时钟、真网络。给一个固定时钟和脚本化模型，就能断言「第 3 步应该请求审批」。

**3. 可移植。** 同一个内核跑在 Node、浏览器、边缘运行时上，差别只在注入了什么。

**4. 可解释。** 出了问题能回放现场：当时时间是多少、模型返回了什么、审批怎么决定的，都在记录里。

## 代价

- 多一层间接：想读时间得 `clock.now()`，不是 `Date.now()`。
- 装配变复杂：少了某个端口，对应能力就真的不存在（工具会从可见集里消失）。
- 容易误用：在核心里偷偷 `await fetch()` 会立刻破坏上面四条，而测试未必发现。

## 确定性到哪里为止

| 是确定的 | 不是确定的 |
| --- | --- |
| 给定输入序列 → 状态与效果序列 | 模型的输出（外部服务） |
| 工具路由、权限决策、上下文组装 | 真实文件系统在你脚下的变化 |
| 压缩决策（给定预算与 token 计数） | 网络延迟、超时 |

所以「重放」成立的前提是：**把不确定的东西录下来**，重放时喂回去。模型响应、工具结果都是这样处理的。

## 对集成者意味着什么

- 你的每个端口实现都是可替换的，别假设内核知道你的实现细节。
- 需要可测的宿主，注入固定时钟与脚本化模型，不要 mock 模块。
- 不要在核心里找「重试逻辑」——重试发生在执行者一侧（runner 与适配器），因为只有它知道 I/O 出了什么错。

## 一句话

**内核负责「想清楚」，宿主负责「真的做」。** 这条分界线就是端口。
