# Security

## Experimental status

volto is experimental software. It has not been security-audited and must not be used in
production.

It executes commands and code generated by a model, reads and writes directories you grant
it, and accesses the network and credentials you configure for it. Erroneous model output,
software defects, misconfiguration or untrusted input can corrupt files, leak data or
cause other unintended consequences.

## Threat model: what is defended, what is not

**volto defends against "the model makes a mistake"** — hallucinating an `rm -rf`,
editing a file it should not, running a command in the wrong directory, or turning an
exploratory action into irreversible damage. The sandbox boundary, the permission matrix
and human approval all reduce the cost of such mistakes.

**volto does not promise to defend against "the model is induced"** — prompt injection
carried by file contents, web pages or tool output it reads. This is not a missing
feature; it is an **architectural conclusion**:

`bash` is a free-text tool. As long as the agent can submit arbitrary shell commands,
per-tool-name grading is only an **upper bound**, not a **guarantee** — a single `bash`
call can do anything that a separately named tool would be denied. We proved one such
path: writing a script into `.git/hooks/post-commit` inside the workspace makes every
subsequent commit execute it as the host user, completely bypassing the sandbox. Paths
like this are not unique; closing the known ones would not make the rest disappear.

Classifying command content ("detecting dangerous commands") blocks naive attacks but not
deliberate evasion, while creating the impression that it blocks them. **We judge that
illusion more dangerous than doing nothing, so we do not build it.**

The risk labels on approval cards ("pushing to a remote cannot be undone" and the like)
are **not** the rejected classifier. They take no part in any permission decision, do not
change allow / deny outcomes, and do not claim to cover the set of dangerous commands —
the full command is always shown above the label, and the label only helps you read the
command already in front of you faster. A missing label weakens no boundary.

If your scenario requires defending against an induced model, run volto in a disposable
VM or container and let the host provide isolation.

## Actual boundary strength

**The sandbox only governs file effects.** The three modes `read-only` / `workspace-write`
/ `danger-full-access` define the **writable range**. Network egress, process visibility,
CPU and memory are outside this vocabulary — a command under `workspace-write` can use the
network normally.

The backends are macOS seatbelt (`sandbox-exec`) and Linux bubblewrap (`bwrap`). They are
not semantically equivalent: on Linux, denied reads are implemented by masking with an
empty tmpfs, so a process that already holds an fd can keep reading. Such differences are
marked one by one as PARITY NOTE in code comments. Other platforms currently have no
isolation backend.

**The Network port's egress policy is tool-level, not system-level.** The allow/deny lists
in the `egress` section of `~/.volto/config.json` (the legacy `egress.json` is still read)
apply only to the `web_fetch` / `web_search` / `http_query` tools: exact hostname matching,
denylist wins, denied requests receive a structured 403. The model's own transport does not
go through this channel (configuring egress cannot affect provider connections), and no
process started from bash (curl, pip and so on) goes through it either — "commands under
`workspace-write` can use the network normally" from the previous paragraph does not change
when an egress policy is configured. Treating this list as a machine-level outbound
firewall is a mistake.

**Parameter-level permission rules apply only to named tools that declare parameters.** In
the `permissions` section of `~/.volto/config.json` (the legacy `permissions.json` is still
read), `pathPattern` applies only to tools that declare a path argument (`read_file` /
`write_file` / `edit_file` / `ls` / `grep` and so on), and `hostPattern` applies only to
`web_fetch` / `http_query`. `bash` declares neither — its command body is free text, not
an argument — so **no path rule constrains it**, and `curl` is likewise unaffected by
`hostPattern`. To block access to a domain, configure the `egress` section (which also
cannot stop curl inside bash, as noted above). A rule can never cross the sandbox
ceiling: in a `read-only` session, an `allow` rule still will not let a write happen.

**Command-prefix rules are likewise not a boundary, and their text-to-effect mapping has
known deviations.** `commandPrefix` in the `permissions` section of
`~/.volto/config.json` applies only to tools that declare a command argument (currently
only `bash`), and only accepts "a single simple command containing no shell
metacharacters"; any compound command, command substitution, environment-variable
assignment or quoted expansion still prompts as usual. Its failure mode is therefore
**asking more**, not blocking less — the opposite direction from the "dangerous-command
classifier" rejected by SAFETY.md (where a missed detection means allow). Two deviations
must be understood: bash uses a persistent session by default, so earlier commands can
leave aliases, shell functions or a rewritten `PATH` such that a textually matching command
actually runs something other than the program you think; and the rule does not constrain
`cwd`. Its accurate meaning is "this command text is no longer asked about", not "permission
to run a program". To genuinely limit what bash can do, tighten the sandbox mode or use a
disposable environment.

**"Always allow" only writes the rule for you; it raises no ceiling.** The "Always
allow …" button on an approval card writes a `commandPrefix` rule into the `permissions`
section of `~/.volto/config.json` — exactly equivalent to a rule you add by hand. It is
clamped by the same ceiling (an `allow` rule under `read-only` does not admit writes),
carries the same R1/R2 risks (it applies across projects, and the current turn may still
ask once more), and has the same known deviations (aliases / `PATH` / `cwd` in the
persistent session are unconstrained). If saving fails, the call still runs as "allow
once"; a bookkeeping failure does not reject the tool call. To revoke, delete the entry
from the file.

**Command hooks in the `hooks` section of `~/.volto/config.json` run in the host process,
outside the sandbox.** They share the trust level of the `permissions` / `egress`
sections: user-edited, host-read, invisible to the model. **Under a sandbox mode** the
model cannot write `~/.volto` (the writable range is only the workspace and temp dirs;
credential-directory read denial is covered below; `danger-full-access` does not isolate,
and bash can write there — that mode's premise is full host trust), so injecting hooks
requires local filesystem access — host trust domain, the same threat level as planting a
`.git/hooks` script in the workspace, not a new attack surface. Three execution semantics
matter: a hook's **stdout never enters the model context** — only the exit code and (on
deny) the first stderr line participate in the decision, so printing more cannot pollute
the prompt; every hook has a **10-second timeout**, after which it receives SIGTERM and the
call is denied fail-closed; a **malformed (or invalid) hooks configuration rejects that
configuration, not the session** — loading failure logs a startup warning and builds the
session with no configured hooks. This is the opposite direction from `egress`
fail-closed behavior (a bad config rejects the whole build) and is deliberate: egress
rejects a "permit" default, while hooks reject only "the rules did not load", and stopping
the whole service buys no security. Two more hook-only surfaces to remember: a hook's
**stdin carries model-controlled data** — preToolUse / postToolUse ctx contains tool input
and tool results, all model-produced; a hook that indiscriminately executes stdin as
commands (`eval`, piping `jq -r` into a shell) executes model output inside the host trust
domain and gives away the entire "defend against model mistakes" position; and hook child
processes **inherit the host environment verbatim** — unlike sandboxed children, which
strip `*API_KEY*` / `*TOKEN*` credential variables, hooks get the full environment and a
hook that needs a clean environment must clear it first. The cost: if you rely on a hook to
intercept dangerous operations and the hooks configuration happens to be broken, that
session runs **without that interception** — hooks are guardrails, not boundaries; the
boundary is in the previous section.

**`~/.volto/memory/` is project long-term memory writable by the model and must be treated
as untrusted reference content.** T11 memory is written by the model through the
`remember` action of the `memory` tool, isolated per project (`<projectId>.jsonl`;
`global` keeps only the data model — T11 has no user write entry point), stored in
`~/.volto/memory` alongside credentials and attachments, unreadable by sandboxed
processes. Injected retrieval text carries a fixed "reference, not instruction" header and
records a `context_reminder(kind: "retrieval")` audit event; even so, **memory poisoning is
outside this project's defensive promise** — the model can write arbitrary text that is
retrieved again in later sessions, the same tier as model-writable files/plans and a direct
consequence of "defend against model mistakes, do not promise to defend against an induced
model". Another known boundary: memory is single-process append-only with no cross-process
lock; concurrent writers to the same project file can lose updates.

**The only read target that is specifically protected is volto's own credential directory**
(`~/.volto`; denied on the shell, filesystem and LSP-child sides — see the LSP paragraph
below). The reason is closed-loop privilege escalation: a sandboxed process that could read
`auth-secret` could forge the gateway's auth cookie and take over the control plane meant
to constrain it. For the same reason, environment variables named like `*API_KEY*` /
`*TOKEN*` / `*SECRET*` / `*PASSWORD*` / `*CREDENTIAL*` are stripped before entering a
sandboxed child.

**`.volto/spill/` inside the workspace is not the credential directory; the two point in
opposite directions and must never be merged.** Oversized tool results are spilled to
`<workspace>/.volto/spill/<sessionId>/<toolCallId>.txt` and **must** be readable back by
`read_file` — "the full text is never lost" is a design goal, the opposite of the
attachment store, which deliberately lives in `~/.volto/attachments` so the model cannot
read it back. The workspace `.volto/` has nothing to do with `~/.volto` under the home
directory; when the workspace root happens to be the home directory, `~/.volto/spill/`
appears, but it is spill data and the credential-denial code path never reads it (verified
across the whole branch in review). The two should never be "conveniently merged". Spilling
happens in the host-side runner process, outside the sandbox child.

**Language-server (LSP) child processes start with the same-tier `SandboxConfig` as the
session, with a read boundary as wide as the shell / file tools (again excluding only
`deniedReadPaths`), but the configuration is not a copy of that one.** It **does not enable
`network`** (Seatbelt `(deny network*)` / bwrap `--unshare-net`), adds
`strippedEnvPatterns`, keeps the credential directory `~/.volto` in `deniedReadPaths`, and
strips `*API_KEY*` / `*TOKEN*` / `*SECRET*` variables before entering the child — language
servers do not need the network, so blocking it costs nothing. But the sandbox only defines
the **writable range and a few denied read paths**: everything outside `deniedReadPaths`
remains readable, so `lsp_hover` and diagnostics can in principle bring file contents from
outside the workspace into the model context (the known shape of the "read boundary").
Three more known limits: in read-only mode a language server cannot write its own cache
(large repos get slower — the price of isolation); in-flight LSP requests **cannot be
cancelled**, the longest wait is bounded by the request timeout, and a timeout kills the
child and starts a new one on the next call; non-TS/JS languages have **no built-in
default** and must be registered in the `lsp` section of `~/.volto/config.json`, otherwise
the tool returns a copy-pasteable config snippet instead of failing to build. The language
server is itself a **third-party binary**, treated as an untrusted child inside the
sandbox — under restricted modes it gets no network and no provider credentials
(`danger-full-access` does not isolate, consistent with the shell / file tools: it then
inherits the host process network and environment, including provider credentials), but it
can read whatever it can read.

**sqlite handles are not governed by the sandbox; the boundary comes from three explicit
rules.** sqlite is an **in-process** connection of the gateway, so the sandbox (which only
governs a child's file effects) does not apply; the constraints live in the opener:
① the database path is realpath-checked and must fall inside the workspace, failing closed
otherwise; ② `db_query` uses a read-only handle (`readonly` + `PRAGMA query_only = ON`), so
the SQLite engine rejects writes rather than a regex prefilter; ③ `ATTACH` / `DETACH` /
`VACUUM INTO` / `load_extension` are explicitly rejected — `query_only` does not cover these
four, and each can bypass workspace containment to open arbitrary files. Write capability is
split by mode: `db:write` is granted only when the host judges the session writable (false
in `plan` / `read-only`), when false `db_exec` is **not registered at all** (invisible to
the model), and when true it is still `WRITE_HIGH` and subject to a second removal by the
read-only ceiling. `better-sqlite3` is a native module; if it is not installed, the first
open returns an `isError` carrying the install command.

**The host's own credentials are outside the protection scope.** Directories such as
`~/.ssh`, `~/.aws` and `~/.kube` remain readable by sandboxed commands. `SSH_AUTH_SOCK` is
also deliberately kept — stripping it would break `git push`, which `workspace-write` is
supposed to allow. Under the "defend against model mistakes" threat model this is a
reasonable trade-off; if your threat model differs, see the previous section.

**The gateway only listens on loopback.** Bindings other than `127.0.0.1` / `localhost` /
`::1` are refused at startup, because the frontend can name any absolute path as the
project root and the agent executes arbitrary commands — exposing it to the network is
equivalent to handing over the whole machine. Every route except `/health` requires
authentication.

## Responsible use

- Grant volto only the smallest directory scope it needs to do the job.
- Prefer a disposable VM, container or dedicated development environment.
- Back up files it can reach; writes under `workspace-write` have no undo.
- **Do not expose credentials you are not willing to risk.** It can read everything you
  let it read.
- Read the command before approving it, especially approval cards under the `ask` mode.
- `danger-full-access` disables all isolation; use it only when you fully understand the
  consequences.
